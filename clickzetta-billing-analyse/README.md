# Account Billing Cost Analysis Tool

Collects Lakehouse metering/billing data from `sys.information_schema.instance_usage` via cz-cli and produces a visual HTML dashboard. When compute cost anomalies appear, it drills down for cluster-level attribution using `sys.information_schema.job_history`.

The dashboard UI is bilingual (English / Chinese, defaults to English) with an in-page language switch.

## Directory Structure

```
clickzetta-billing-analyse/
├── README.md               ← this file
├── SKILL.md                ← Agent Skill definition (Kiro entry point)
├── scripts/
│   ├── auto_collect.py     ← permission gate + cz-cli data collection
│   └── inject_html.py      ← HTML template injection script
├── template/
│   └── billing_analysis_template.html  ← HTML dashboard template
└── output/                 ← runtime artifacts (gitignored)
    ├── data.json           ← raw collected data
    ├── summary.txt         ← condensed summary (for the Agent to read)
    ├── insights.json       ← analysis conclusions generated by the Agent
    └── billing_analysis_report.html  ← final HTML report
```

> `template/resource_notes.js` is deprecated: `instance_usage` has no cluster-name dimension, so resource purpose is inferred from the SKU type, and cluster-level attribution is handled by the job_history methodology.

## Requirements

- `cz-cli` installed with at least one connection profile configured (`cz-cli profile list` to check)
- Python 3.9+ and `python-dateutil` (`pip install python-dateutil`)
- The target profile's user needs:
  - the **`instance_admin`** role (required to query `sys.information_schema.instance_usage`)
  - **use vcluster** permission on at least one workspace (required to run queries)

## Manual Usage

### 0. Permission gate (required before collection)

```bash
python3 scripts/auto_collect.py --profiles <profile1,profile2> --check-only
```

Only profiles that print `✅ passed` can be collected; `❌` explains the missing permission.
### 1. Data collection

```bash
# Collect the last 6 months (default), for a given profile
python3 scripts/auto_collect.py --profiles <your_profile>

# Specify a time range and multiple profiles
python3 scripts/auto_collect.py --from 2026-02 --to 2026-06 --profiles p1,p2
```

- `instance_usage` is an **instance-local** view: one profile = one region's data. The script reads `region_name` from the data as the region label — no hardcoded account_id / region mapping.
- Profiles without sufficient permission are **skipped** and recorded in `skipped_regions`, then flagged as "no permission / not collected" on the dashboard.

Output: `output/data.json` + `output/summary.txt`

### 2. Generate insights.json

This step is done by the Agent (LLM): it reads `summary.txt` and writes the analysis to `output/insights.json`.
For manual use, follow the JSON schema defined in SKILL.md (use the `workspace/sku_name` format for `details[].item`).

The dashboard is bilingual, so the Agent produces `_en` fields alongside the Chinese ones (see the "Bilingual (Option A)" note in SKILL.md). When `_en` is missing, the dashboard falls back to the Chinese text.

For compute cost anomalies, follow "Step 2.5 drill-down methodology" in SKILL.md to run `job_history` queries via cz-cli for cluster-level attribution.

### 3. HTML injection

```bash
python3 scripts/inject_html.py --no-backup
```

Output: `output/billing_analysis_report.html` (open directly in a browser)

## Using via the Kiro Agent

In a conversation, type something like:
- "Analyze the cost for the last six months"
- "Show the consumption per workspace for this environment"
- "How much did each SKU cost"

The Agent first confirms which cz-cli profile to use and checks permissions, then runs the full flow (collect → analyze → generate report).

## Data Sources

| Purpose | Source |
|---------|--------|
| Base metering (amount/usage, by sku_category × sku_name × workspace) | `sys.information_schema.instance_usage` (discounted amount `total_after_discount`) |
| Compute drill-down attribution (cluster, job type, idle-CRU detection) | `sys.information_schema.job_history` |

Regional coverage is entirely determined by the cz-cli profiles the user provides — nothing is hardcoded.
