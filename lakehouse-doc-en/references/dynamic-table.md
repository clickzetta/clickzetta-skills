# Dynamic Table

> **[Preview Release] This feature is currently in invite-only preview. To request access, please contact Singdata through the official website.**

A Dynamic Table is a type of automatically maintained data table in Singdata Lakehouse. It describes data processing logic through a SQL query definition, with the system performing automatic incremental computation and persisting the results. Unlike regular tables, the data is automatically refreshed by the system — no manual INSERT/UPDATE is needed. Unlike views, a Dynamic Table **stores actual data**, so queries directly read precomputed results without re-executing the SQL.

## Core Features

1.  **Query Results as Tables**: Dynamic Tables generate datasets dynamically based on their defined query. Each query may produce a fresh dataset — the content of the Dynamic Table.
2. **Incremental Refresh Mechanism**: Dynamic Tables support incremental refresh, triggering query execution and content updates only when the underlying data source changes. This significantly improves data processing efficiency, especially for large-scale data.
3. **Operation Restrictions**: Since data is generated by queries, Dynamic Tables do not support traditional direct data operations such as `UPDATE`, `DELETE`, or `INSERT`, ensuring data consistency and accuracy.

## Use Cases

*   **Data Warehousing**: Dynamic Tables can store processed and transformed data for downstream data analysis and reporting.
*   **Real-Time Data Applications**: For scenarios requiring real-time data updates, Dynamic Tables provide rapid data refresh capabilities to maintain data timeliness.
*   **Data ETL Processes**: During Extract, Transform, and Load (ETL) processes, Dynamic Tables can serve as intermediate storage for transformed datasets.

## Differences Between Materialized View and Dynamic Table

In terms of implementation, Dynamic Tables in Lakehouse evolved from traditional materialized views. While they share some commonalities, their positioning differs significantly.

**Materialized View: Performance Optimization Tool**
A materialized view is a special type of view that precomputes and stores query results, significantly improving query efficiency. Unlike regular views, materialized views save computation results in a table-like structure, allowing the optimizer to automatically recognize subsequent similar queries and directly use pre-stored results — reducing redundant computation and accelerating query speed.

**Dynamic Table: An Efficient Tool for Data Processing**
Dynamic Tables focus on data processing. While they can also improve query performance, they do not rely on the query optimizer's automatic rewriting. Materialized views must keep data up-to-date for query rewriting to work, whereas Dynamic Tables — oriented toward processing scenarios — may not always have the most current data.

**Limitations of traditional materialized views (not present in Lakehouse)**:

1.  Can only be based on a single base table. Materialized views cannot be based on complex queries (i.e., queries with joins or nested views).

2.  Materialized views are not necessarily incrementally refreshed — different systems implement this differently. A few systems implement incremental computation in some operators to save computing resources and speed up processing.

**Advanced Features of Dynamic Tables**:

1.  **Incremental Identification and Optimization**: Supports file-level incremental identification in big data environments, enabling real-time incremental reads, computation optimization, and write optimization.
2.  **Intelligent Decision-Making**: A Cost-Based Optimizer intelligently selects full, incremental, or partial incremental computation to accommodate different query requirements.
3.  **Real-Time Task Operations**: Provides mechanisms such as data version management, rollback, and rerun capabilities, offering comprehensive support for real-time task operations.

**Data Freshness Considerations**:

* Materialized views require immediate data updates to ensure query rewriting accuracy. When base table data changes, Lakehouse uses a scheduled refresh mechanism to keep materialized view data up to date.
* Dynamic Tables focus more on flexibility in data processing, adjusting data lag based on business definitions rather than requiring real-time updates.

## Dynamic Table Management Guide

*   **Creating Dynamic Tables**: Users can define new Dynamic Tables using specific syntax and specify the SQL query statement for data transformation. For detailed syntax and steps, see the [Create Dynamic Table](create-dynamic-table.md) documentation.
*   **Dropping Dynamic Tables**: If a Dynamic Table is no longer needed, use the `DROP TABLE` command to remove it. Before executing the drop, ensure data has been backed up or is confirmed to be no longer needed, as this operation removes both the Dynamic Table definition and its data. For detailed syntax and steps, see the [Drop Dynamic Table](drop-dynamic-table.md) documentation.
*   **Viewing Dynamic Table Refresh History**: Use the `SHOW DYNAMIC TABLE REFRESH HISTORY` command to view the refresh history of a specified Dynamic Table, allowing you to monitor refresh job execution status (success/failure), runtime, incremental/full refresh mode, and number of records processed.

## Data Processing and Incremental Computing

Dynamic Tables play an important role in data processing. By defining query statements, users can implement data extraction, transformation, and loading (ETL). At the same time, Dynamic Tables support incremental computing, triggering data updates only when the data source changes, effectively reducing data processing time and resource consumption. For detailed information on incremental computing and data processing with Dynamic Tables, refer to the [Data Processing and Incremental Computing](dynamic_table_summary.md) documentation.
